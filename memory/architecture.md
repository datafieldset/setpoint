# Architecture

## Stack
Next.js 14 (App Router), deployed on Vercel. Neon Postgres (serverless driver, `@neondatabase/serverless`). Auth.js (email/password). Stripe (live). Web push (VAPID). Coinbase Exchange public API for all real price/candle data (no API key needed, granularity in seconds: 60/300/900/3600; some timeframes are aggregated client- or server-side from a smaller real granularity — see below).

## Key files
- `lib/signals.js` — the real core. `computeSignals(candles, tfKey, th, opts)` runs every detector, returns `{ signals, warming, snap }`. Individual detectors: `detectReversalWatch`, `detectCoil`, `detectSwing`, `detectSwingEarly`, `detectMomentum`, `detectVolumeSpike`, `detectRsiOversoldOverbought`, `detectVolumeBuildingEarly`, `detectQuietAccumulation`, `detectBreakoutBreakdown`, `detectGrindSignal` (Grind Up/Down), `detectWhaleFlow`.
  - `SIGNAL_RATES` — the static promotion table, `"Label|tf|dir": { rate, runs }`. Only source of static "proven" status.
  - `PROVEN_THRESHOLD = 0.58` — the one, real bar every verification path checks against.
  - `TESTING_SIGNALS` — array of signal *names* (not combos) that log/show to admin even while unproven.
  - `KILLED_COMBOS` — array of exact `"Label|tf|dir"` strings filtered out of `computeSignals`'s output entirely, before logging or display — for combos conclusively proven dead on real, substantial samples. Different from "just not promoted": this stops it firing at all.
  - `ALL_SIGNALS` — the full, honest registry of all 15 real signal names + plain-English descriptions of what each does. Single source of truth for "how many signals do we have."
  - `provenContext(label, tfKey, dir, liveGate, regime, regimeGate)` — THE single, shared function that answers "is this currently verified." Do not reimplement this logic anywhere else; every time it's been duplicated, the duplicate has drifted and caused a real, found bug (see lessons-learned.md). Checks, in order: (1) static promotion + live-gate override if enough recent data, (2) regime-only path — a combo with no static entry can still be "proven" purely from its own, current record in one specific market regime, if that regime has ≥`REGIME_ONLY_MIN_SAMPLE` (10) real trades and clears 58%. Returns `{ tag, boost, phrase, rate, isLive, verifiedVia, regimeStage }`.
  - `getLiveVerifiedGate()` — queries `signal_track`, returns `{ gate, regimeGate }`, both rolling-20-trade windows (`LIVE_GATE_WINDOW = 20`, `LIVE_GATE_MIN_SAMPLE = 5` to trust the overall gate). `gate` keyed `"label|tf|dir"`, `regimeGate` keyed `"label|tf|dir|regime"`.
  - `brandName(label)` (in `lib/brand.js`) — maps internal signal names to customer-facing display names (e.g. "RSI oversold" → "Snapback", "Volume spike" → "Surge", "Reversal watch" → "Rebound"). Internal names are never renamed to match — the internal name is the real database key across all of `signal_track`'s history; renaming it would either require a risky data migration or silently split a signal's rolling-window history. When looking at internal data, always show both names together to avoid confusion.
- `lib/timeframes.js` — `TF` object: per-timeframe `pctMin`, `gran` (Coinbase granularity seconds), `aggFactor` (how many real, fetched bars get combined into one bar of this timeframe — 30m and 4h are aggregated from smaller real granularities), `cooldownMs`.
- `app/page.jsx` — the whole client dashboard in one large file. Key components: `Dashboard`, `Guide`, `AdminPanel`, `SignalCatalog`, `Landing`, `Auth`, `UpgradeGate`. Sub-views use `?view=` query param + `openSubView`/`closeSubView` helpers for URL-persisted navigation.
- `app/WatchLiveContent.jsx` — the public, no-login "Watch Live" proof page, pulls from `/api/public-stats`.
- `app/api/cron/check-signals/route.js` — the real detection + logging + push engine, runs as the GitHub Actions cron (see infrastructure.md). Scans a `LOOKBACK_MS` window (30 min) of real, closed bars per (coin, tf), not just the single most-recent bar — a bar whose whole real lifetime is close to the cron's own check interval can flip true→false between checks and get missed entirely otherwise. Logs every real signal detected, regardless of tier (see lessons-learned.md on why). Push notification is gated separately, after the DB insert succeeds, using a *freshly re-fetched* live/regime gate (not the one fetched once at the top of the run) — this was a real, found bug: a run checking many coins/timeframes sequentially could use stale gate data by the time it got to a later signal.
- `app/api/open-positions/route.js`, `app/api/resolved-positions/route.js` — power "Open Alerts" / "Recently Resolved" on the dashboard.
- `app/api/public-stats/route.js` — powers Watch Live. Only counts trades from a `(label, tf, dir)` that is *currently, genuinely* `proven` via `provenContext` (static or regime-only), each combo capped to its own real, most-recent 20 trades (never a signal's whole, all-time history — see lessons-learned.md).
- `app/api/signal-catalog/route.js` + `SignalCatalog` component in `app/page.jsx` — admin-only "Signals" page, the full, honest census: all 15 signals, real current status, per-timeframe rates, plain-English condition breakdowns (trend/bias splits) pulled from the most recent saved `/api/backtest` run.
- `app/api/backtest/route.js` — the deep, slow, full walk-forward simulation across every real coin/timeframe. Not called live from any UI — Na runs it manually and uploads the resulting `.md` report. Saves every real bucket (including trend/bias condition splits) to the `backtest_results` table on each run — that table is what `signal-catalog` reads for condition breakdowns, so it never needs to re-run the slow simulation itself.

## Core, repeated patterns worth knowing
- **A signal is "proven" three possible ways**: static (SIGNAL_RATES) confirmed or overridden by a real, recent live-gate record; or purely regime-only (no static entry needed) if that specific market condition currently clears the bar on ≥10 real trades. Every surface that shows "verified" anywhere must go through `provenContext` directly — never re-derive this.
- **Bias/trend/regime context** — `biasContext`, `trendContext`, `marketRegime` in `lib/signals.js` compute real, current market condition (aligned/against broader bias, aligned/against local trend, ranging/trending/high-vol/low-vol regime). Several signals hard-gate their own detection on these (e.g. Momentum 4h long only fires proven when against-bias; Volume spike long only fires when bias-aligned) — these gates live inside the individual detector function, not as a generic, reusable mechanism.
- **Levels formula** — `levels(price, atr, dir)`: entry at current price, stop at 1.5× ATR, target at 2× that risk (2.0R). Same formula for every signal; a slow, sustained-move signal (Grind Up) using this same, tight, single-bar-volatility-based stop was directly investigated as a possible root cause of its weakness — tested and ruled out (see lessons-learned.md), the underlying "recent up-bars predict more upside" idea itself doesn't hold, not the stop distance.
- **Deep, independent backtesting from the sandbox** — when investigating whether a signal actually works, don't trust the live `/api/backtest` report alone for small samples; fetch deep, real Coinbase history directly (`fetchDeep`-style paged candle fetch), run `computeSignals` against a **fixed, trailing window** (not the full, growing slice — that's O(n²) and will time out) for real performance, and cross-check across all four watchlist coins before trusting a promising small sample from one coin alone.
