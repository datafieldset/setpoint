# Version history (condensed)

Earlier history (v9-v14ish): initial build, pricing (`lib/pricing.js`), landing page, guide page, backtest report generation, whale-flow tracking, regime-aware verification concept introduced.

v15.x: Landing/guide copy rewrites (Morning Brew voice). Sub-view URL persistence fix. News feed removed (Reddit/Bluesky 403 confirmed). Market Meter moved to 5m, colored by real direction, scope note added. Live win rate threaded from the real gate.

v16.x: Regime-aware verification introduced properly — `getLiveVerifiedGate()` returns both overall and regime gates, `signal_track.regime` column added. Root-cause fix: live gate can only refresh/demote an already-statically-proven signal, never promote a statically-weak one on a lucky rolling window (found after a real, direct audit showed the blended, all-time track record at 44.5%, well below what "verified" should mean). 10 weak signals formally cut with dated, real evidence in `SIGNAL_RATES` comments. Coil and Swing added as testing signals.

v17.0-17.3: Swing (RSI-extreme + structural break) and Swing Early (fires at the turn, no confirmation wait) added. `computeSignals` refactored into 11+ separate detector functions. Testing-tier signals extended to persist correctly in open-positions/recently-resolved (were disappearing after their triggering bar passed).

v17.4-17.9: Push/logging decoupling bug found and fixed (client-side). Both crons' scheduling reliability fixed (2h trigger + internal 5-min loop, see infrastructure.md). Rolling live percentage surfaced on testing-signal cards. Whale Flow rebuilt to require a real oversold/overbought condition alongside the large trade (plain size alone had been cut). Real, live percentage display bugs found and fixed across `/api/open-positions` and the client's own, duplicated verification checks — consolidated onto `provenContext` directly.

v18.0-18.9: Regime-only verification extended so a combo can be "proven" with zero static promotion, purely from a strong, current, condition-specific record (≥10 trades, ≥58%). Signal catalog (`/api/signal-catalog` + `SignalCatalog` UI) built — full, honest census of all 15 signals. Public-stats (`Watch Live`) redesigned twice: first to only count each verified combo's own real, most-recent 20 trades (not all-time history); second, deeper fix to stop retroactively counting stale history the instant a combo became regime-verified. Momentum promoted (4h, against-bias gated) after it was found to have caught a real market move with zero data behind it, because it had never been promoted or added to testing — led to the standing "always log everything" principle. Full, direct, independent audit run across all 15 signals/6 timeframes against deep BTC history; several large-sample, conclusively-dead combos added to `KILLED_COMBOS`; Grind Up's stale static promotions retired after a deeper audit directly contradicted them. Swing|15m|bear and Volume spike|15m|bull promoted after directly deepening thin, promising samples across all 4 coins.

v19.0-19.2: Found and fixed the same regime-blindness bug (public-stats and signal-catalog both silently ignored regime-only verified signals entirely) — this was the deeper root cause behind "the dashboard shows real wins the public page doesn't reflect." Both names (internal + customer-facing brand) shown together in signal-catalog to prevent confusion. Cron push decision fixed to re-fetch fresh live/regime gate data right before sending, instead of reusing a snapshot from the start of a potentially long-running check.

v19.7: Whale Flow fully retired (both directions genuinely weak on deepened, cross-coin evidence) — see signal-roster.md.

v19.9: Neon compute-hour quota fully exhausted (real, live 402s from the database) — root cause confirmed directly from Neon's own usage numbers: two separate, overlapping cron workflows kept the database almost never idle. Combined into one workflow, trigger interval stretched from 2h to 5h to match real run duration, and the Sep 25 push-decision re-check fixed to use a short, real cache (90s) instead of fully bypassing it. See infrastructure.md's "Neon compute-hour incident" for the full, real numbers and reasoning.

v19.10: Built the tiered confidence system (established/emerging/early read), replacing the old binary "promoted or invisible" split for admin visibility — real customer-facing logic (provenContext) completely untouched. New, deliberately isolated data path (getFullSignalGate, its own 5-minute cache) so no sample-size floor blocks visibility, without adding to the cron's database load. Real admin feed built into Guide. Also fixed the backtest report's live scoreboard to filter by ALL_SIGNALS, so fully-retired signals (Whale Flow, EMA cross) stop showing frozen, old history as if still active.

v19.11: Automated promotion checking — new, separate, infrequent cron (every 6h, /api/cron/check-promotions) scans every real signal/combo for anything newly qualifying for established or emerging tier with no static promotion yet, sends a real, direct, admin-only push if found. Deliberately never auto-writes SIGNAL_RATES — surfaces the candidate, a promotion still means a real, deliberate decision. This is the direct fix for the recurring root cause behind most bugs found this session: something only ever got caught when a human happened to notice it in chat.

v19.17: Watch Live made honest and readable. The headline said "all 7 verified setups, all-time, every trade" while only 3 setups were actually verified (Swing 15m short, Momentum 4h long, Rebound 1h long), those 3 are slow, and the page showed 7 trades with one in October, which read as broken. public-stats now also returns the setups behind the number (record plus last trade date), `lastTradeAt`, and an `emerging` group: combos in the confidenceTier "emerging" tier (5+ real trades, 55%+), shown clearly separate and NEVER counted in the headline win rate. Retired labels and KILLED_COMBOS are excluded from both groups. New `buildGatesFromRows()` in lib/signals.js builds the unfiltered gates from rows already in hand, so the public route doesn't need a second full-table scan. Copy now says what the page actually is: each setup's last 20 trades, and a setup that slips under the bar leaves the page with its trades. Known remaining gap: verified status is still judged today, not stamped when a trade fired, so history can shift as setups are promoted and demoted. Fix would be a verified-at-fire column on signal_track. Guide Part 1 explains the two groups.

v19.19: Verified status is now stamped when a trade fires. New nullable `signal_track.verified_at_fire` column (added by `lib/schema.js`, run once per instance, shared by the cron, `/api/track` and public-stats), written by the new `verifiedAtFire()` helper in lib/signals.js, which is just `provenContext(...).tag === "proven"` so there is still one definition of verified. The cron now fetches its fresh gate (90s cache) BEFORE the insert so the stamp and the push decision read the same data. `/api/track` stamps from the server's own gate and never trusts a flag from the browser. Public-stats counts a trade if it was verified when it fired, keeps it even if its setup has since slipped (marked "under the bar now"), and excludes trades stamped false. Rows with a null stamp (everything before this) fall back to the old rule, verified today, until the stamped set takes over. `stampedSince` in the response drives the Watch Live note. Known gap: the push decision in the cron still has its own parallel check (`currentlyVerifiedFresh`) next to provenContext, left alone on purpose. Also noticed: `/api/track` is public and takes entry/stop/target from the caller, so anyone could log a fake trade. Worth a separate fix.

v19.20: Backtest fixed to use the live move-size rule. New `thresholdsFor(tfKey, base)` in lib/signals.js is the one place pctMin joins the thresholds; cron, dashboard and both backtest routes use it. Old backtests passed plain DEFAULT_TH, so Momentum fired every bar and Quiet accumulation never did. Momentum 4h long's 93% verified rating pulled (rested on that bug). Full-year BTC re-test of every signal under the live rule: only Swing Early 15m bear holds. Swing-Rebound study (wider stops, longer holds): no edge, nothing built. /api/track (public) now validates label/tf/dir, requires entry within 2% of the live price, and rebuilds the target as exactly 2x risk server-side, closing the fake-trade hole.

v19.20 (continued, same day): (1) Watch Live shows average result per trade in R (win +2R, loss -1R, break-even at a 34% win rate, before fees), headline and per setup; /api/public-stats returns avgR. (2) "Big move underway" heads-up: lib/bigMove.js, called at the top of every check-signals run; BTC 5%+ off its 12h low/high (about 4 a month on a year of data), 12h cooldown per direction in new table `big_move_alerts`, pushed to admins only, labeled not-a-signal. Widen to customers by changing the recipient query in checkBigMove. (3) Monthly killed-signal recheck: scripts/recheck-killed.mjs + .github/workflows/recheck-killed.yml replay every killed combo (5m and up, BTC, live rules) and open a GitHub issue if one clears 58% on 30+ fires, or 40%+ on 100+ fires holding in both halves. Never changes code. (4) Market Meter gets a bigger-picture strip (BTC 12h / 24h / 3-day change) and a flag when a multi-day run is on. Customer tiers: Watch Live already shows an Emerging section (not counted in the headline), so no change.

v19.20 (review + target floor): Added the prove-your-work process (memory/review/, scripts/review.mjs, scripts/verify-live.mjs, CLAUDE.md rule). Built the minimum-target rule (belowTargetFloor / TARGET_FLOOR_RATIO in lib/signals.js; wired into computeSignals, cron, track, open-positions, public-stats, dashboard push) and Na chose three quarters (ratio 0.75): floors 1m 0.225%, 5m 0.525%, 15m 0.9%, 30m 1.275%, 1h 1.875%, 4h 3.375%. Year-of-BTC share kept at 0.5/0.75/1.0 of pctMin: 1m 45/19/9%, 5m 58/24/11%, 15m 69/31/12%, 1h 79/44/20%; win rates flat.

v19.21: Trend Rider, admin-only forward test (lib/trend.js pure rules, lib/trendRunner.js server side, /api/trend, app/TrendRider.jsx, runs inside every check-signals call). BTC, 4h candles built from 1h, enter when a 4h bar closes beyond the prior 20 bars' high/low with price on the right side of its 200-day average, trailing stop 4 ATR, no target, one trade per direction. Replay of 120 days hour by hour through a fake database reproduced the study exactly (6-year: 102 longs +0.35R 43% win, 78 shorts +0.08R 36% win, every trade matched). Pushes to admins only on entry and exit. Focus mode: VISIBLE_SIGNALS is empty, hiding all original signals (see signal-roster.md). Dashboard coins tab shows only Trend Rider for admin, a short "rebuilding" note for everyone else; Watch Live shows a rebuilding message.

## Numbering note
Version numbers are informal, bumped per real, deployed change, tracked in git commit messages (`vX.Y`) — not tied to a formal release process. Check `git log --oneline` for the authoritative, current sequence.

v19.21 review fixes: open-positions, resolved-positions and scoreboard now hide non-visible signals; Trend Rider close/trail updates guarded against double runs; entries only evaluated when the newest due 4h bar is present; panel says so when the 200-day average is unavailable. Known limits: entry is checked on the latest bar only (a cron outage over 4h can miss a breakout); ATR seed depends on the ~75-bar fetch window.

v19.22: Trend Rider is public (panel and /api/trend read-only for everyone; push alerts still admin-only). Short-timeframe bounce study (5m/15m/30m/1h, new-48-bar-low reversal candle, with and without RSI, trailing stop 1 to 2 ATR) found no edge: bounce entries average -0.03R vs +0.02R for entering on any bar, no setting positive on both halves. Scratch: scratchpad/trend/bounce.mjs.

v19.23: Trend Rider on six timeframes (4h, 1h, 30m, 15m, 5m, 1m), public, with a live scoreboard per timeframe (win rate, wins, losses, average R, buys and sells apart, plus a split by crowd mood). Entry is a TOUCH of the 20-bar high or low (not a close). Needs the 200-day average side, RSI above 60 (below 40 for sells) and ADX above 20, the 1h chart (and 4h on 15m) agreeing on the fast charts, and for BUYS price within 20% of the 200-day average. 4h sells skip RSI/ADX. Trailing stop 4 ATR on 4h, 3 ATR elsewhere. Admin push alerts only for 4h and 1h; the other four track quietly. The cron scans every bar from the last 15 minutes oldest first, so the fast charts catch touches between 5-minute runs; stops are checked on finer candles (1h on 4h, 5m on 1h/30m/15m, 1m on 5m/1m). Engine replay (same code as the cron) over history: 4h buys 44% wins +0.51R, 1h buys 39% +0.30R, 30m 24% +0.10R (38 trades), 15m 45% +0.29R, 5m 40% +0.29R, 1m 42% +0.19R. Live runner matched the replay trade for trade on 1m and 5m. lib/trendRef.js holds those reference numbers; scripts/trend-study/ holds the replay and fake-database tests. Bugs caught by the end-to-end test before shipping: newest-first scan kept the wrong touch; re-entering on touches from while the last trade was still open doubled 1m trades.

v19.23 review fixes (independent agent): one failed Coinbase call now costs only the timeframes that need it (allSettled, 8s timeout, 10-minute stale fallback), the whole Trend Rider run is cut off after 20 seconds so it can never stall customer alerts; scan window follows the last successful run (trend_state table) instead of a fixed 15 minutes; trailing stop and best price only ever move in the trade's favour in SQL; push failures can't abort bookkeeping; public /api/trend is cached 15s with a generic error and no DDL from visitors (first-visit fallback only); closed-trade list is 12 per timeframe; panel: removed the wrong 34% break-even tick, early-read label under 10 trades, history trade counts, honest expectations text, buttons with aria-pressed, live region, polling pauses in hidden tabs. Known limit kept on purpose: a trade's entry bar is walked from the bar start, so a pre-touch low can stop it out (cautious, same as the study).
